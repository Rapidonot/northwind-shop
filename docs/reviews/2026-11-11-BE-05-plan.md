### B. Prerequisites on the payment port (P1, P2, P3)

**Confirmation reference (P1).** New `northwind_backend/confirmations.py`:
- `Confirmation(ref, order_id, amount: Money)`.
- `ConfirmationBook`: `verify(ref, order_id, amount)` and single use.
- `issue()` is called only by the test fixture that stands in for the portal control. An AST pin keeps every
  `issue(` call out of `src`.
- References are letters only (`cf_` and 16 capitals), so they never look like card data. They are random, never
  in model input, and the audit writes them as type and length.

`PaymentPort.authorize` and `capture` gain a **required** keyword `confirmation_ref`. The fake checks it inside the
idempotent effect:
- The reference must be known and bound to this order (for capture, the intent's order), in the same currency.
- `authorize` must be for exactly the confirmed amount. `capture` must be ≤ the confirmed amount.
- The first successful `authorize` uses the reference up, and the intent records which reference authorized it.
  `capture` must present that same reference; it is accepted although it is used. Any other reference is refused
  (`confirmation_mismatch`), a fresh unused one for the same order included. After a void, a new authorization needs
  a new confirmation (Approval 1).
- Errors: `confirmation_required` (validation: missing or malformed), `confirmation_mismatch` (validation),
  `confirmation_used` (business).
- A dry run checks the reference and uses nothing up.
- `void`, `refund` and `status` are unchanged: void releases money, and refund has its cap (PAY-06 later).

**Per-order limit (P2).** `ORDER_LIMITS_MINOR` on the payment state. `authorize` above the limit gets
`over_order_limit` (business, escalated). A currency with no limit gets `no_order_limit`. Capture is already ≤ the
authorization. **Placeholder values (Q2):** USD 2,000.00, CAD 2,700.00, GBP 1,600.00, EUR 2,100.00. Every generated
order is under them (computed from the live price table: max USD 1,801.35, CAD 2,669.54, GBP 1,429.67, EUR 2,061.42),
so the replay measures the agent, and unit tests cover the refusal.

**Across instances (P3).**
- The state moves out of the fake instance into `PaymentState`, `FraudState` and `CarrierState`. Those hold the
  intents, assessments and shipments, the idempotency store and its lock, the effects, the caps, the limits and the
  confirmation book.
- `PaymentFake(state=..., scopes=...)` and the others take a state. `PaymentFake()` still makes a private one, so
  FOUND-3 tests keep their isolation.
- Scopes stay per instance (a credential). The one-payment rule, idempotency, the refund cap, one assessment per
  order, one shipment per order and confirmation use hold across every instance on one state.
- Docstrings in `ports.py` and `payment.py` that say "No port carries a confirmation reference" and "hold only within
  one instance" are rewritten.

**Existing tests:** about 84 `authorize(` call sites in `services/backend/tests` and `_driver.py` get a confirmation
through one test helper. This adds a required argument; no assertion changes.

**Decision record:** `docs/decisions/0014-payment-confirmation-and-order-limit.md`. It settles FOUND-3's "on the port
or a named layer above it": on the port contract, so the PAY-01 contract suite checks it on every adapter. If #13 also
takes 0014, whichever row merges second renumbers.

### C. The Orders agent places orders (R1, R2, U2, U4)

**New ports and stubs:**
- `CatalogPort` (reads: `price`, `stock`) with `CatalogTableFake` over the live tables, never the index (hard
  rule 2).
- `OrderStorePort`: `get`, `use_address_on_file`, `confirm`, `escalate`. Each write takes an idempotency key and
  `dry_run`. `OrderStoreFake` is loaded from `data/backend/orders.jsonl` and `shoppers.jsonl`. It allows one confirmed
  order and one escalation per order ID, across instances.
- Audited views for both in `views.py`.
- New named sets: `PAYMENT_PLACE = {authorize, capture, status}` (no void, no refund: hard rule 8, PRD §7),
  `FRAUD_PLACE = {assess, read}`, `CATALOG_READ = {price, stock}`, `ORDERS_PLACE = {get, use_address_on_file,
  confirm, escalate}`.
- The undeliverable-postal-code rule moves from `fakes/carrier.py` to `carriers.py`, so the order store and the
  carrier fake share it. The orders agent gets no carrier scope.

**`agents/orders_place.py`** (actor `orders-subagent`, Haiku via `ROUTINE_MODEL`, `agent_options()` only):
- Task `OrderPlacementTask(order_id, confirmation_ref)`. The prompt is "Place order O000123." The confirmation
  reference never reaches the model.
- Seven tools. Each takes only `order_id`, and `escalate_order` also takes a `reason` enum. A call for any other
  order ID is refused, audited and never reaches a port (L2). The tools:
  - `validate_order`: live stock per line, address deliverable, total from live prices
  - `use_address_on_file`
  - `assess_fraud`
  - `authorize_payment`
  - `capture_payment`
  - `confirm_order`
  - `escalate_order`
- **What the model sees:** issue codes, line count, the total in minor units and its currency, the fraud decision,
  score and reasons, the payment status and minor amounts, the order status and the escalation reason.
- **What it never sees:** intent, assessment or shopper IDs, tokens, addresses, confirmation references or
  correlation IDs. No sequential ID reaches model input, so cassettes don't depend on run order (this matters for
  concurrent recording).
- **Gates in code, not the model:**
  - `authorize_payment` needs this run's `validate_order` with no blocking issue, and a fraud `allow`. The amount is
    the validated total, so the schema has no amount field.
  - At most 2 authorize attempts per run, the 2nd only after a `soft_decline`.
  - `capture_payment` needs this run's authorized intent, held in the run state.
  - `confirm_order` needs a capture equal to the total.
  - `use_address_on_file` runs only after `address_undeliverable`, with a file address in the same region that is
    deliverable.
- **Keys (U2):** built only from task IDs: `O000123:fraud.assess`, `O000123:order.address_on_file`,
  `O000123:payment.authorize:1` and `:2`, `O000123:payment.capture`, `O000123:order.confirm` and
  `O000123:order.escalate`. A rerun after `audit_incomplete_run` repeats the same keys, so it repeats the same first
  results.
- **No second write after doubt (U2):** `RetryPolicy` gains `retry_codes`. Writes use `WRITE_POLICY`, which retries
  only `service_unavailable` and `audit_unavailable`, where nothing ran. A `timeout`, `unexpected_error` or
  `audit_incomplete` on a write makes no second call. The step is `uncertain`, the run escalates with
  `uncertain_write`, and `reconstruct_order` shows it `open`, or settled by a later read, as in BE-08. `UNEXPECTED`'s
  message stops claiming a retry is safe.
- **Routine resolutions (R2):**
  - Address typo: `use_address_on_file` (Q7), then validate again.
  - Soft decline: one more authorization under key `:2`. **Fake issuer behaviour (Q1):** with
    `PaymentState(soft_decline_retry_approves=True)`, a soft-decline token's next attempt for the same order under a
    new key is approved. The default `False` keeps FOUND-3's behaviour.
- **Escalated:** fraud review, out of stock (held until BE-04), hard decline, a second soft decline, over the order
  limit, a confirmation mismatch, an uncertain write.
- **Escalation context (R2, U4):** built by code from the run state, never from model text. It holds:
  - the order ID and reason code;
  - each finished step's value;
  - the failures as `AgentFailure` envelopes (references only);
  - uncertain actions with their keys;
  - amounts in minor units from `StepResult.value`;
  - a recommended action from a fixed table.

  If the run ends with neither a confirmed order nor an escalation, code escalates it (`not_finished`), so a run
  never ends silently.
- **Outcome:** `placed | escalated | failed`, from the stores and the run state, never from the summary.
