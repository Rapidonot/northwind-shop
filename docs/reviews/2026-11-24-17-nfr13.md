# Row #17: NFR-13 (partial), first-token estimate

NFR-13: "First streamed token within 2 seconds at p95". This row records one estimate, as the plan and decision 0021
say. Retrieval p95 and checkout p95 are not measured here, and there is no load test.

## How it is measured

The runner buffers each whole response to scan it, so a client cannot see first token through it (#17a). The
estimate therefore adds two parts:

1. **Live: time to first upstream byte.** The runner logs `first_byte_ms` per request in the ledger.
   - It is `message_start`, not the first text delta.
   - On a call whose response starts with a thinking block, first byte comes before the thinking, so it is a lower
     bound for first token.
2. **Local overhead, in replay** (`services/gateway/tests/test_nfr13_first_token.py`, `main()`).
   - **Path:** POST `/api/chat` to the first `token` SSE event. It goes through the real gateway, mcp-rag over the
     `northwind_16` index with the live FastEmbed embedder (mcp-rag's default), mcp-catalog over the fixtures, the
     real CLI and the output check.
   - **The model is a paced fake** that answers at once. Its first delta ends mid-sentence, so the check's hold-back
     is included. Deltas are spaced 0.05 s apart: `['The Larchpell Larch Area Rug is a ', 'flatweave rug [P0178]. ', 'It lies flat.']`.
   - **Turns:** 1 warm-up turn, then 30 sequential turns over the 5 smoke questions. Every turn made exactly
     1 model request.

## Estimate

- **Headline:** `assistant-smoke` first byte p95 + local p95 = 1,644 + 377 = **2,021 ms**.
  That is about 2 s: just over the target on this estimate.
- **On the cart path:** 1,911 + 377 = 2,288 ms.
- **Caveats:**
  - Adding two p95s is conservative, because the parts are not both at their worst on the same turn.
  - It leaves out the gap from `message_start` to the first text delta, which is not logged. That gap is longer when
    thinking comes first.
  - It is one run per suite, at low volume.
- **Recorded as NFR-13 partial, not met** on this estimate.
