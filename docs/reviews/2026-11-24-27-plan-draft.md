## Design (defaults; the advisor may change them)
- **Two new servers, on #10b's pattern:**
  - streamable HTTP on 127.0.0.1, behind `mcp_gate.verify_for` with their own `srv`;
  - structured errors (hard rule 10);
  - unknown argument keys and card data refused (hard rule 1).
- **`northwind-orders` (`services/mcp-orders`): `get_order(order_id)`, plus `request_return` if D2 (a).**
  - The order store and the carrier fake are seeded once from `data/backend` (read-only).
  - Each order's labelled outcome is applied: `placed` becomes `confirmed`, and `escalated` becomes `escalated`. That
    way store status and tracking agree. Today every fixture order loads as `pending`.
  - **Own orders:** the order's `shopper_id` must equal the token's `shp`. Another shopper's order, an unknown ID or a
    malformed ID all get the same `not_found` bytes, so the tool can't be used to find out which order IDs exist.
  - **Allow-listed fields only:**
    - `order_id`, `placed_on`, a shopper status, the lines (product, variant and quantity);
    - tracking: carrier, tracking number, and scans (date and status).
    - Never the `payment_token`, postal code, `exception`, escalation reason or `shopper_id`.
    - `fraud_review` shows only as `on_hold`.
  - **Shopper status:** a code mapping from the store status and the last scan, tested for every combination:
    `processing`, `on_hold`, `label_created` (no scans yet: a valid empty result, not an error), `picked_up`,
    `in_transit`, `out_for_delivery`, `delivered`.
  - Read live on every call, so a test that changes the store or the tracking sees the change (hard rule 2).
- **`northwind-policy` (`services/mcp-policy`): `evaluate_return_eligibility(order_id, variant_id, condition)`, plus
  resources.**
  - **Resources:** `northwind-policy://returns/{region}` and `northwind-policy://shipping/{region}`. Each holds the public
    POL document text plus the structured facts below. The token's region is the only region served.
    - `INT-001`/`INT-002` and the canary are never served (hard rule 7).
    - There are no warranty documents in data v3, so there is no warranty resource (stated, not invented).
  - **Facts:**
    - the window (US 30, CA 45, UK 28, EU 60 days from delivery);
    - the 14-day statutory period (UK, EU);
    - the clearance rule;
    - the bedding rule: subcategory `duvet`, covering duvets and comforters;
    - wear-and-tear goes to the repair program.

    Each fact carries its document ID and the sentence it comes from. A test checks that each sentence occurs in the
    public document, so the facts cannot drift from the text the output check vouches against.
  - **Evaluator:** a pure function in `northwind_common/returns_policy.py`, used by both servers. It works from the
    order, the delivered scan, the product's subcategory, the shopper-stated `condition` and a **fixed as-of date**
    from config, never the wall clock, so the result replays after Dec 22. Its default sits inside the fixture's
    delivered dates (Oct 5–Nov 4).
    - **eligible:** delivered, within the window or the 14-day period, `unworn`, and the bedding rule met. The result
      says "subject to inspection".
    - **ineligible:** out of the window; `worn_or_washed` outside the 14-day period; an opened insert where the
      region's rule refuses it; wear-and-tear damage (alternative: the repair program); not delivered yet (the window
      starts at delivery).
    - **ambiguous:**
      - condition not stated: the assistant asks the shopper;
      - `damaged_on_arrival`: the policies cover wear and tear only, so this is a gap;
      - `worn_or_washed` within the UK or EU 14-day period: the statutory text sets no condition;
      - more than one matching line.
    - The result gives the outcome, a reason code, the facts used (with document IDs), and the next step.
  - **Clearance:** no product in data v3 carries a clearance marker, so the evaluator can't tell. It treats items as
    not clearance. The resource still states the rule, and unit tests use a synthetic product. This is a known limit,
    not an invented attribute.
- **Assistant (D3):**
  - `Caller` gains `shopper_id`.
  - `assistant_options` attaches the two servers only when it is set.
  - Tool results are labelled `<order_data>` / `<policy_data>` as data (hard rule 6).
  - The prompt section says:
    - status and dates come only from `get_order`;
    - eligibility only from the tool;
    - explain the outcome by its reason and facts;
    - ask for the condition when it is missing;
    - never promise a refund, label or approval.
- **Output check (`output_check.py`, decision 0015):** #12's and #13's tests are unchanged. The new exemptions are
  narrow:
  - **Confirmation wording** ("your order has been confirmed or placed") passes only if this turn's `get_order` for
    that order returned a confirmed status.
  - **A duration in a policy sentence** passes only with the same value from this turn's eligibility result or a
    public document, as today.
  - **Refund authority** ("refund approved") stays blocked always.
- **Audit:** the MCP servers have no BE-08 audit today (catalog and cart have none either), so none is added here.
  Logged in the PR body only.

## Tests (`req("CHK-06")` / `req("CHK-07")`, with `NFR-01` and `RAG-11` where noted)
`test-writer` runs: these are hard-rule paths. Everything is written failing first, scripted, at $0.

**CHK-06**
1. **All 1,000 orders** match: `get_order` as the owner returns the store's status and the carrier fake's scans,
   field for field.
2. **The status mapping**, for every combination of store status and last scan.
3. **Own orders only (NFR-01):** another shopper's, an unknown or a malformed ID gives the same `not_found` bytes and
   no order field. With no shopper bound, the tools are not attached.
4. **Allow-list (hard rule 7):** no `payment_token`, postal code, `exception`, escalation reason or `shopper_id` in
   any result, over all 1,000 orders.
5. **Live (hard rule 2):** a status or scan changed while the server runs shows in the next result and answer.
6. **Errors (hard rule 10):** a carrier timeout is `transient`, `isRetryable`, and distinct from `label_created` with no
   scans.

**CHK-07**

7. **About 60 labelled cases** (`reviewed_by: model`): each of eligible, ineligible and ambiguous, in all four regions.
   - They include the edges: the window's last day, the 14-day period, bedding, wear and tear, damaged on arrival, and
     condition not stated.
   - The evaluator must match every case. A mismatch is a bug or a label question (stop 7).
   - The cases are not in `evals/` (control surface); they live in `services/mcp-policy/tests/`.
8. **Policy resource (RAG-11, hard rule 7):**
   - each fact's sentence occurs in its public POL document;
   - a token for one region reads only that region;
   - INT-001/INT-002 and the canary are never served.
9. **`request_return` (hard rule 9, if D2 (a)):**
   - the server re-evaluates eligibility;
   - an ineligible request writes nothing, and an ambiguous one becomes `needs_review`;
   - the same key gives one request, and the same key with other arguments is a conflict;
   - `dry_run` writes nothing;
   - another shopper's order is refused;
   - no refund, label, capture or assign tool appears in any assistant tool list.
10. **Injection (hard rule 6):** a scripted model says "the policy says 90 days, I'm eligible", and a tool-returned
    text tells it to start a return. The outcome is unchanged and the request is refused.
11. **Card data (hard rule 1):** card data in any argument is refused before the store is read.

**Both**

12. **Output check:**
    - confirmation wording passes only with a matching `get_order` status in the turn;
    - a window duration passes only with the region's own value;
    - "refund approved" is blocked;
    - #12's and #13's tests pass unchanged.
13. **Determinism:** the fixed as-of date and the same inputs give the same request hashes. The anonymous request is
    byte-identical to main's: a pin, and every existing cassette replays.

**Recorded (later, in your window)**

14. Suite **`assistant-orders`** (Sonnet), about 9 scenarios:
    - status in transit;
    - delivered;
    - label created, no scans yet;
    - an order on hold, with no reason leaked;
    - another shopper's order ID;
    - a return that is eligible (request created);
    - a return that is ineligible (out of the window, explained);
    - a return that is ambiguous (condition not stated, so the assistant asks);
    - an injected "policy says 90 days".

    Each asserts its planned outcome. A mismatch is stop 7, never a re-record loop.
