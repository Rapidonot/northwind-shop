## 2. Changes

**xdist (C2).** Add `pytest-xdist` to the root dev group (`pyproject.toml`, `uv.lock`). In the Makefile, a single
`PYTEST_PAR := -n auto --dist loadgroup` goes on the pytest line of `test` (which `ci` runs) and of `check`.
`test-integration`, `record`, `e2e`, `eval-*` and `enrich` stay serial and unchanged. The replay plugin already
refuses xdist outside replay (`pytest_plugin.py:52`). CI's unit step becomes `uv run pytest -n auto --dist loadgroup`.
The flags go on the command line, never in `PYTEST_ADDOPTS` or `addopts`: nested `uv run pytest` runs inside the
tests inherit the environment, and `addopts` would reach `make record`.

**What the static survey says is safe:** ledger (tests that write it set `LLM_LEDGER_PATH` to a tmp path; one exception below), proxy and
scripted ports (bound to 0), env (per worker, monkeypatched), tmp dirs (`tmp_path` is per worker), Postgres
(every connecting file is integration/e2e-marked; the six files with per-test marks get checked one by one).

**Candidates for serial:** tests that run `make`, `git` or a nested `uv run pytest` with `cwd=REPO`
(`test_ship_marker`, `test_wiring`, `test_rag08b_citations`, `test_promotion`, `test_drift_extra`,
`test_advisor_reviewer`), and `evals/tests/test_enrich.py::test_make_enrich_with_no_window_open_exits_before_any_call_and_leaves_every_file`,
which reads the real `~/.northwind/ledger.jsonl` (PROGRESS open items; it already fails when another worktree
writes the ledger, and xdist does not change that unless a worker writes the real ledger). The risks are `index.lock` from concurrent git, concurrent `uv` syncs and nested
`.pytest_cache` writes. A nested pytest also inherits `PYTEST_XDIST_WORKER`, which turns the plugin's xdist refusal
on in the child. Policy for anything that fails only in parallel: fix the isolation first (own tmp path, env without
`PYTEST_XDIST_*`) where that leaves what the test proves unchanged; otherwise mark it
`xdist_group("checkout")` so that those tests run one at a time on one worker. Every touched test is listed in
the PR body. No assertion is loosened, and none is skipped or deselected.

**CI triggers (C3).** `on: pull_request` plus `push: branches: [main]`. `check_jobs` reads the PR head's checks
by `workflow/name`. Each CI job appears there twice today and once afterwards, so `REQUIRED_JOBS` is still met.
What goes: the bare-head push run. What stays: the pull_request run on the merge ref (what `ship`'s merge commit
lands), and the push run on `main` after the merge. A branch pushed without a PR gets no CI, and `finish` pushes
and opens the PR in one step.

**Split (C5).** New job `python-integration`, with the same pgvector service, env (`LLM_MODE: replay`), uv sync,
fastembed cache and extension step as `python`, then `uv run pytest -m integration`. `python` loses its
integration step and keeps lint, mypy, scan and the unit tests. No job-level `if` and no `continue-on-error`.
`tools/ship.sh` `REQUIRED_JOBS` gains `CI/python-integration`, and `tests/ship/test_ship.py` `JOBS` gains it too,
so the parametrized refusal tests (fail, skipping, pending, cancel) cover it.

**Ship ordering (advisor, 2026-11-23; also in the PR body).** Once DEV-1 ships and the runner syncs, `ship`
refuses any open PR whose head has no `CI/python-integration` check ("job missing"). Neither open row is
blocked: 12b ships before DEV-1, and #16 merges main (with DEV-1) before its own ship, so its head runs the new
`ci.yml`. Any other PR opened before DEV-1 needs main merged in, or a push, before it can ship.

**Timeouts (C4).** 2x the slowest measured job, rounded up to 5 min, and at least 10 min for any job that
starts a Postgres service or installs a browser, because their setup varies. The two new job totals are built
from the slowest steps of the current `python` job: setup about 21 s (containers, checkout, uv, sync, cache),
mypy 18 s, scan 10 s and unit 903 s give `python` about 952 s. Setup about 21 s plus integration 1,172 s gives
`python-integration` about 1,193 s. The default is 360 min, so each value is a tightening. A timeout is a
failure, and `ship` refuses it.

| Job | Slowest | `timeout-minutes` |
|---|---|---|
| python (lint + unit, serial basis) | ~952 s (15.9 min) | 35 |
| python-integration | ~1,193 s (19.9 min) | 40 |
| eval-gate | 3m16s | 10 |
| e2e | 2m24s | 10 (floor) |
| portal | 0m31s | 5 |
| Guard / eval-gate-main | 2m30s | 10 (floor) |
| Guard / baseline-label, eval-integrity-main | 10 s | 5 |

**Concurrency (C4, #12's note).** Both workflows get `group: ${{ github.workflow }}-${{ github.ref }}-${{
github.event.action == 'synchronize' && 'push' || github.run_id }}` with `cancel-in-progress: true`. Only
`synchronize` runs share a group, so a new push cancels the old SHA's run, which `ship` never reads. Label,
edit, open and reopen runs, and the push run on `main`, each get their own group and are never cancelled. A
plain workflow + ref group is not used. Without `cancel-in-progress`, a new push would wait behind the old run.
