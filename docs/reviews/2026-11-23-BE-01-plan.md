## Design
**Caller:** staff or an internal event, never the shopper. Nothing touches the gateway, the assistant or `services/common`.

**Planner (Sonnet):**
- Uses `ASSISTANT_MODEL`, read only, with `llm.py` unchanged.
- Gets one tool, `submit_plan`, and no data tools. Turn cap 2.
- The request text is data (hard rule 6). It is refused before the model if it holds card data (hard rule 1).
- Code validates the plan:
  - every kind is on the allow list: `payment_fraud`, `tracking`, `unsupported`;
  - IDs match the regexes;
  - every ID appears verbatim in the request, so the planner cannot invent one;
  - at most 4 concerns, duplicates removed.
- A plan that fails validation, or no plan at all, gives a `FAILED` result with a validation failure, and nothing runs.

**Subagents (Haiku), each with only its own scoped tools (hard rule 8):**
- `payment_fraud`: the existing `run_orders_check`.
- `tracking`: new `agents/returns_track.py`, the Returns subagent's read-only slice. PRD §7's Returns row allows the "carrier agent".
  - One tool, `track_shipment(tracking_number)`, through `AuditedCarrierPort(CARRIER_READ_ONLY)`.
  - Its task binds the order to `tracking_number_for(order_id)`, and the handler refuses any other number, as `orders_check._refuse` does.
  - BE-06 (#28) extends this agent later.
- `unsupported` (refund, cancel, address change, other): no run. It becomes a `not_supported` failure with the alternative `escalate_to_staff`, so it is annotated, never dropped.

**Parallel:** the subagent runs execute together in an `asyncio.TaskGroup`, each under its own deadline. Each has a child audit context with the orchestrator's correlation ID (`run-<uuid>`).

**One result:** an `OrchestratorResult` holding:
- one status, derived like `derive_status`: complete, partial or failed;
- one section per concern;
- every failure with its attempted action and alternatives;
- one correlation ID;
- an `answer` built by code from the step values (C1). There is no second model call.

**Audit:** `orchestrator.run` attempt and outcome, plus `orchestrator.plan` (kinds, and IDs by reference). The request text is recorded only as its type and length.

**Demo:**
- `uv run python -m northwind_backend.orchestrator "<request>"` in replay prints the one result.
- `make` is not changed, because the Makefile is on the control surface.

## Tests (tagged `req("BE-01")`, plus BE-02/BE-08 where noted; failing-first log kept)
1. **Split (scripted Sonnet):** a two- and a three-concern request become typed tasks. These are refused: an invented ID, an unknown kind, more than 4 concerns, card data in the request, no plan.
2. **Parallel:** stub runners wait on a barrier that opens only when every run is in flight. Run one after another, they would deadlock and time out. A delay test shows wall time ≈ the max, not the sum.
3. **One result:** one status, one section per concern and one correlation ID. The answer is built from the values. An unsupported concern is annotated with its alternatives.
4. **End to end (scripted, $0):** Sonnet planner plus both Haiku subagents in parallel through `agent_options()` and the proxy path, giving a complete result.
5. **BE-02:**
   - an injected carrier `TIMEOUT` gives `PARTIAL`: the Orders section stays intact, and the failure names the attempted action and its alternatives;
   - a `HANG` past the deadline gives a `deadline` failure, and the other runs are kept;
   - a planner model failure gives an annotated `FAILED`, never a crash.
6. **BE-08:** the orchestrator events and subagent runs share one correlation ID; the request text is never in the audit; `reconstruct_order` still holds.
7. **Least privilege and data:**
   - the planner's allowed tools are exactly `{submit_plan}`;
   - `returns_track` gets exactly `{track_shipment}` and its view is read-only;
   - the existing money-name pin (`test_be08_views.py` `ROOTS`) already walks `northwind_backend/orchestrator`;
   - the subagent prompts carry IDs only.
8. **Recorded, later:** suite `backend-orchestrator`, about 5 requests:
   - two concerns;
   - three concerns including an unsupported one;
   - two orders;
   - a carrier timeout;
   - an instruction-injection attempt in the request.

   The replay test asserts the planned outcomes. Estimated spend is under $0.10, with `RUN_BUDGET=1`.
