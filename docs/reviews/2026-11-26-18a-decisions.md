## D2. Row #27 PR 2's L4 (a card split between an order number and a digit key) needs a pin of yours changed

**What happened.** `holds_card_data({"order_id": "O411111", "idempotency_key": "1111111111"})` is False on main and on this
branch. The joined check cannot see it: the digits touch the letter `O`, and the argument names make the gap wider than 12.
`request_return`'s pair check skips every pair that includes a well-formed order number. That is pinned by
`test_the_split_card_check_never_refuses_a_good_request_for_its_key` (`services/mcp-orders/tests/test_chk07_request_return.py`), with
keys `42424242` and `4111-1111-11` that must be `recorded`. Both possible fixes change that pin:
- (a) **Pair the order number's digits with the key's.** A good order number plus an all-digit key of 7 digits or more passes Luhn by
  chance in about a quarter of cases or more, so good requests get refused at random. Not recommended.
- (b) **Refuse a key with a digit group longer than 6** (single separators joined, as `cards.py` joins them), as a `validation`
  error that asks for a random key, before any card check. With the 6 digits of an order number that leaves at most 12 joined
  digits, which can never be a card. **Recommended.** It refuses the pin's `4111-1111-11`, which is the pin change you would make.
  Measured at $0: none of the 1,612 idempotency keys in every recorded suite has a digit group longer than 6 (the return keys are
  `RetO000800dmg01` and `ret800sealed01`), so no recording changes.

**Waits on it:** only L4. It is pinned as a strict xfail (`services/common/tests/test_18a_cards.py`), so the fix has a failing-first
test ready. With (b) the change is in `services/mcp-orders` (`request_return` and its tool description) plus the pin; `cards.py` stays
as it is.
