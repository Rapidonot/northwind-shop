## What this does (decision 0023)

- **A demo sign-in behind a flag.** `POST /api/session/shopper` binds one fixed synthetic shopper, S0188, to the
  signed session, only with `NORTHWIND_DEMO_SIGNIN=1` (set by `make dev`). With the flag off it is a 404 for every
  method. No portal picker.
- **`services/mcp-orders` with one read-only tool, `get_order`.**
  - It answers only for the shopper (`shp`) and region in the signed token. No schema takes a shopper ID.
  - Another shopper's order, an unknown number and a malformed one all get the same `not_found` bytes.
  - It returns allow-listed fields only: never the payment token, postal code, exception, escalation reason or shopper
    ID.
  - It reads the order store and the carrier fake on every call (hard rule 2).
- **Signed-in turns only.** The tool and the `ORDERS_RULES` prompt section are attached only when a shopper is bound.
  An anonymous turn's request is unchanged byte for byte (four prompt hashes pinned to main's).
- **`shp` beside #11's `qf`.** `shp` is valid only on a shopper token for northwind-orders, and `qf` only for
  northwind-rag, so a token carrying both verifies nowhere.
- **No output-check exemption** (the user's option B). `output_check.py` equals main's. "Your order was placed" stays
  blocked on every turn. With the order number between the noun and the verb ("Order O000418 has been confirmed") it
  was never blocked; see "Known limits".
- **No real order in what the model always sees.** `ORDERS_RULES` uses placeholders, and `get_order`'s examples use
  O012345, which is no order.

## Known limits (not fixed here)

- **Raw status codes:** two of the six recorded answers show a code (`in_transit`, `label_created`). PR 2's D9 adds a
  plain wording.
- **Order statuses and past dates are controlled by the prompt only** (threat model, Open). **Owner, by the user: PR 2
  (CHK-07), with D9:** a stated order status must match this turn's `get_order` result. The exception is "your order
  was placed / confirmed" with nothing between the noun and the verb.
  - **"Order O000418 has been confirmed" passes the check,** even for an order on hold (advisor M-1). The pattern is
    main's and the gap is older, but this row's answers name order numbers: three recorded ones say "Order <number>
    was placed on <date>", truthfully. PR 2 closes it.
- **`CLAUDE.md`'s `make dev` line is out of date** (it lists neither mcp-orders nor the sign-in flag). It is control
  surface; the user edits it later, not in this row.
- **L4 (low):** the sign-in POST has no `Origin` check, like the gateway's other POSTs.
- **mcp-orders' derived ports (50000–59999)** are inside macOS's ephemeral range, so one can occasionally be taken.
- **The flag-off 404's header order** differs from a real missing path's (informational).
- **Split cards:** the card checks' digit join now crosses IDs and other fields, so digits in an ID can sit between
  the two halves of a card split across two blocks. Scripted runs are deterministic, so this cannot flake.
- **The on-hold and no-number scenario checks are strict on wording:** a harmless phrase could fail a later re-record.
- **No signed-in browser journey:** the sign-in is tested through the API (SA-01's picker is window B's).
