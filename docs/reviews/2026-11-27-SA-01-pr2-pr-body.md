## What was built

**The v2 look** (`docs/design/{home-tabs,product,product-specs-reviews,assistant-panel,bag}.png`). The user approved it
after three rounds.
- **Department tabs:** All plus each department with its count, in catalog order (the order each first appears). The
  selected tab is filled black. The tabs are tightened to fit at 1440px with the panel open. When they don't fit, the
  bar scrolls sideways with outlined ‹ and › buttons, never a fade, and the selected tab is always scrolled into view.
- **Home:** the hero with 3 featured tiles (P0001, P0004, P0121), each showing its full name and its live price or
  range.
- **Product page:**
  - a breadcrumb and the description;
  - colour chips with swatches (an unknown colour gets no swatch, never a guessed one) and size buttons;
  - a full-width ADD TO BAG;
  - a 4-column specifications grid with only the record's own fields (hard rule 5);
  - reviews: "Showing 3 of N" and "Show all N reviews", through the new portal-only `list_reviews`, rendered as
    plain text (hard rule 6).
- **The assistant panel:**
  - it narrows the page, with Close, the "Northwind AI assistant" heading and the disclosure;
  - it scrolls messages, and the input is pinned at the foot;
  - "Talk to a person" is a normal button, and the cart is a compact "Cart (N)" block;
  - the suggestions are the recorded smoke questions, word for word (`e2e/questions.json`: `product`, `care`,
    `false_policy`). They show only while the chat is empty, and "New conversation" empties it again.
- **Only the products on screen are priced** (hard rule 2):
  - `browse_products` gains `product_ids` and `priced: false`;
  - grids read pages of 24, and "Show more" reads the next page;
  - the hero and the bag read only their own IDs, and the tab counts read no price.

**The bag's controls.** ADD TO BAG, − / + and Remove call new gateway routes. `shopper-portal` holds exactly the three
cart writes (the user's stop 5 yes). Each click gets one letters-only key; each session gets one stable turn.
- **The paths are POST only: `POST /api/cart/items`, `POST /api/cart/quantity`, `POST /api/cart/remove`.** The plan
  had `PATCH`/`DELETE /api/cart/items/{sku}`. The user accepted the change, for two reasons:
  - the session middleware binds sessions to exact paths only, so `/api/cart/items/{sku}` would never get a session,
    and the cart tools would refuse it (`session_required`);
  - with POST only, one write guard covers every write: a JSON body, the `X-Northwind-Portal` header, and
    `Sec-Fetch-Site`/`Origin` same-origin. No variant ID ever goes into a URL or the access log either.
  - Both pins have these paths exactly: the path-to-method allow-list and the session-path set.

**Order history.**
- **`list_orders`:** a new portal-only tool on mcp-orders, returning the signed-in shopper's own orders in their
  region, newest first, with the allow-listed fields only.
- **`GET /api/orders`:** it merges those with the gateway's demo orders. An anonymous shopper gets 200
  `{"signed_in": false, "message": …}` with no `orders` key, so it is never an empty list (hard rule 10); the portal
  shows a sign-in prompt. It was a 401 until the first `make e2e-scripted`: the browser logs every 4xx as a failed
  request, so a normal anonymous visit to Orders broke the "no errors" journey.

**The demo checkout: CHK-02's portal control** (`services/gateway/src/northwind_gateway/checkout.py`, decision 0027).
- **The summary** shows the live bag's lines, total, delivery text, `POL-RETURNS-<region>` and a letters-only digest.
- **Pay (demo):**
  1. It requires the demo sign-in (the user's decision).
  2. It reads the live bag again and refuses, before any confirmation exists: a changed digest, an issue, the order
     limit, the per-shopper order cap, the order-number cap, and stock that is already short.
  3. Then comes the one `issue` call in the repo.
  4. Then BE-04's inventory store and `orders_place`'s handlers run in fixed code: validate, fraud, authorize,
     commit, capture, confirm, `finish`. There is no model.
  5. A placed order empties the bag, judged by a fresh read. "No longer available" comes with BE-04's substitutes.
- **Idempotency:** one result per (shopper, key), under a lock per shopper. While the bag still holds lines of a paid
  order it couldn't empty, Pay is refused (`already_placed`).
- **No card field** anywhere (hard rule 1).

**Also in this PR:**
- **PR 1's open item F4:** `CartReader` now closes its HTTP client (`a8f4ad2`).
- **e2e set-up:** the scripted model counts its requests (`GET /_requests`), and the e2e gateway has the demo sign-in
  on.

- **The cart writes are POST only.** The reason is under "The bag's controls"; the user accepted it.

  uses. Neither leads to a model call; the runtime guard and the AST pin cover that (advisor-reviewer L4).
- **A refusal for paid lines still in the bag removes whole lines** (re-review N4). If the shopper raised such a line's
  quantity on purpose afterwards, all of it is removed, not just the paid units. That is the safe direction: any later
  order needs a fresh summary and a press. The portal rereads the bag and the summary after it.
