## Why

#32 (window B) re-recorded answers for items whose first-search context changed with DATA_VERSION 3.
Three of those items have recorded refinements, and the re-recorded answer replaces them. Main allows a
replaced refinement only when the baseline's answerer prompt part changed (12a), and #32 keeps #12's
prompt (`prompt-150c1ee8` at both `5539421` and `e92d0d2`). So `Guard / eval-integrity-main` would
block #32's ship, and that check is never waived. The lesson from 12a: the relaxed rule lands on main
first, in its own PR.

## Scope (exactly)

`evals/src/northwind_evals/integrity.py` and `cli.py`'s `cmd_integrity`, plus tests and records.
integrity.py stays stdlib-only, because Guard's `integrity-main.py` loads main's copy with nothing from
the PR and already calls `integrity_problems`. That is how the new exemption reaches Guard once this
merges.

1. **Per-item context exemption.** New `CONTEXTS = "evals/contexts/dense-only.jsonl"` and
   `context_changed_items(commit) -> set[str]`. An item counts as changed only when it is in the file
   at `commit` and its `chunks` value differs from the base's **both** at HEAD **and** on disk.
   - Fail closed: the item is missing at HEAD or on disk; the file is missing at the base, at HEAD or
     on disk: then nothing is exempt.
   - A duplicate `item_id` or an unreadable line raises `RuntimeError`, like the refinements parser.

   `changed_refinements` skips a removed or changed base entry `(item, n)` only when the answerer
   exemption holds, or when `item` is in that set. One item's change never exempts another. New
   entries pass, as now.
2. **Report.** `replaced_refinements` lists every base entry that changed or was dropped under either
   exemption, as today (item_id, n, old, new), plus `reason`: `"answerer"` or `"context"`.
   `cmd_integrity` prints it as now (one JSON line each). The only change in cli.py is the comment on
   the print loop, which today names the answerer alone.
3. **12a's F2.** A deleted `refinements.ndjson`, at HEAD or on disk, is always a problem, under either
   exemption. `changed_refinements` loses its early `return []` and checks deletion first.

Not in scope: Guard's `integrity-main.py` printing the replaced list (12a's F1, still row 12b), and
12a's G1/G2/U1.

### Decisions (recommendation first)

- **D1, what counts as "different chunks":** the whole `chunks` value (ids, order and text), ignoring
  `index_version` and `retriever_id`, which change on every re-ingest. Text the model saw changed, so its
  refinements may change. The alternative compares only the chunk_id list, which is narrower. On the real
  data both give the same result, because all 10 changed items differ by chunk id.
- **D2, reason when both exemptions hold:** `"answerer"`, the broader one, for every entry. The
  alternative is a list of reasons.
- **D3, `test-writer`:** it writes gap tests only into the new test file (below), and 12a's file stays
  untouched. The alternative is read-and-report only, as in 12a.
