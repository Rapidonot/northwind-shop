## Changes, PR 2
- **Cart routes:**
  - `POST /api/cart/items`, `PATCH /api/cart/items/{sku}`, `DELETE /api/cart/items/{sku}`;
  - they go through the existing cart writes, which `shopper-portal` gains;
  - each takes a client idempotency key and passes the header and `Origin` check.
- **Order history:**
  - `GET /api/orders` reads the seeded orders through a new portal-only `list_orders` on mcp-orders, by `shp`, plus the
    gateway's demo orders for the same `shp`;
  - an anonymous shopper gets a sign-in prompt;
  - it shows `book.py`'s allow-listed fields only.
- **S1, the demo checkout.** `services/gateway/src/northwind_gateway/checkout.py` holds the backend fakes in process:
  `PaymentState`/`PaymentFake` (`northwind_backend/fakes/payment.py`), the fraud fake, a demo order store and the
  audited views. The sequence:
  1. `GET /api/checkout/summary` reads the cart and live prices, and returns the lines, the total and a digest. It
     issues no confirmation.
  2. Pressing the **Pay (demo)** UI control sends `POST /api/checkout/pay` with `{digest, idempotency_key}`, the header,
     the `Origin` and the session. The route recomputes the summary, refuses a changed digest and checks
     `DEFAULT_ORDER_LIMITS`.
  3. It reserves stock (S2), then calls `confirmations.issue`, bound to the order ID, currency and exact total. This is
     the only call site in the repo.
  4. Validate, fraud, authorize, capture and confirm run in code, in a fixed order. A failure voids the payment and
     releases the reservation.
  5. The cart is cleared. The order appears in `/api/orders`.
- No card field of any kind. `shopper-portal` gets no payment or checkout tool.
- Decision `docs/decisions/0027-portal-checkout-control.md` covers:
  - the gateway as the one confirmation issuer;
  - CHK-02's control built here;
  - demo orders kept apart from the seeded store: the assistant's `get_order` does not see them, a known limit.
- **No model call:**
  - the checkout never uses BE-05's `run_order_placement`, which uses `ROUTINE_MODEL`;
  - `checkout.py` imports neither `northwind_common.llm`, `northwind_assistant` nor `northwind_backend.agents`;
  - $0.
  - If any of these is needed, I stop and report the suite and the spend.
- **The pin:**
  - `test_nothing_under_src_issues_a_confirmation` keeps its current check on `services/backend/src` unchanged.
  - A new check covers every other `services/*/src`, `agents-external/` and `partner-agent/`. It flags imports of
    `northwind_backend.confirmations` or its book, and calls to that book's `issue`, through aliases and attribute
    chains. `session.py`'s local variable `issue` is not a confirmation call and is not flagged.
  - Exactly one allowed site: the call in `checkout.py`'s pay function. No exemption by file or by name.
  - The pin's comment and the docstring in `confirmations.py` (lines 14–15) say SA-01 builds CHK-02's portal control,
    and that this route is the only issuer.
- **S2, the reservation: needs your answer (stop 7).** No BE-04 reservation path exists (#25 is `todo`, and
  `cart_store.py:10` says "reservation belongs to checkout (CHK-05)").
  - **Recommended:** a minimal checkout reservation on mcp-catalog, `reserve_stock(lines, idempotency_key)` and
    `release_reservation`, portal-only:
    - all-or-nothing under the live store's lock, so the last unit is never oversold;
    - idempotent per key;
    - added to `PORTAL_CATALOG_TOOLS`, refused for every other agent;
    - PROGRESS records it as "built under SA-01 for CHK-05's checkout reservation", with a cross-reference in #21 that
