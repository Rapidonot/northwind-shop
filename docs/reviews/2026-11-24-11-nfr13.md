The plan's (1): measure what query understanding adds to first-token time. This uses #17's method
(`docs/reviews/2026-11-24-17-nfr13.md`): live first byte, plus local overhead measured in replay.

## The run
- **Command:** `DATABASE_URL=…/northwind_16 uv run --offline python services/gateway/tests/test_nfr13_first_token.py --qu --runs 30`
- **Time and head:** 2026-11-24, at head `cdf5e07` plus this arm. The raw report is
  `docs/reviews/2026-11-24-11-nfr13-qu.json`.
- **Path:**
  - the real gateway, CLI and output check;
  - mcp-rag over the `northwind_16` index with the live FastEmbed embedder;

  after 3,510 ms, W1's measured p95.
- **Turns:** 1 warm-up turn, then 30 sequential turns, 10 of each kind. Every turn made exactly 1 model request.

## What each kind exercised (the advisor's L5)

The report labels each turn by its position in the message list. A static check (`rules_plan` and `plan_claim`)
confirms what each message does:
- **The 5 rules-filtered messages:**
  - none goes to Haiku and none names a product;
  - "Queen sheet sets in white", "A navy fleece in M" and "Wool rugs in 5x8" make a colour or size claim;
  - "Pants under $50" and "rain jackets that are in stock" make a claim through the live filter's
    `eligible_products` call. With the catalog attached, as in the run, all 5 make a claim.
- **The 5 Haiku-routed messages:** all are routed (`needs_model`). In live mode each hits the deadline and then runs

- **Not checked:** the run itself does not record `qu_path` per turn.

## Local overhead: POST to first token

| Kind | p50 (ms) | p95 (ms) | What it pays |
|---|---|---|---|
| plain (the 5 smoke questions) | 398 | 417 | nothing extra: the rules path, under 1 ms |
| rules-filtered (5 browsing messages with colour, size, price or stock) | 388 | 406 | the live filter's `eligible_products` call and the planned search: nothing measurable |
| Haiku-routed (5 multi-part messages) | 1,085 | 1,124 | the 700 ms deadline, then the rules plan |

- **Comparison:** #17's plain p95 was 377 ms. Today's 417 ms is the same path; the machine was not idle (window B).
- **Warm-up turn:** 1,103 ms, not in the table.

## Estimate (#17's method: smoke first-byte p95 1,644 ms + local p95)

| Message kind | First token, p95 estimate |
|---|---|
| plain | 1,644 + 417 = **2,061 ms** |
| rules-filtered | 1,644 + 406 = **2,050 ms** |
| Haiku-routed | 1,644 + 1,124 = **2,768 ms** |

- **The 0.7 s on routed messages comes from the deadline, not from Haiku's answer.** In live mode W1's Haiku
  latency (p95 3,510 ms) always loses to the deadline, so a routed message pays the deadline and then answers from
  the rules plan. That is the deadline gap in the PR body.
- **Share:** routed messages are 2.3% of eval first messages (7 of 308) and 7.1% of red-team messages (2 of 28). On
  traffic like the eval set they sit above the p95, so the overall p95 estimate stays about **2.06 s**, against
  #17's 2,021 ms.
- **NFR-13 stays partial and not met.**
