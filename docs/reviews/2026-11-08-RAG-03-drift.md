### Cause: the dense distances differ, not the method

- **Distance noise across platforms reaches at least 2e-5.** Pairs 2e-5 apart flipped (EV-082, EV-014).
  pgvector's own float32 arithmetic is off from an exact computation by at most **3.7e-7** on macOS (all
  113 queries, top 100; re-measured with exact float32 values as 3.708e-7, `cost.txt`). That cannot flip a
  2e-5 gap. On x86 this bound is an inference, not a measurement. So the embeddings themselves differ:
  fastembed/onnxruntime 1.31.1 on x86_64 (MLAS kernels picked by CPU features) against arm64. pgvector's
  arithmetic could still flip EV-029's 1.96e-7 gap on its own, even with identical vectors.
- **The embedder depends on batch shape, and the Nov 4 vectors cannot be regenerated** (corrected; this
  first said "not stable even on one Mac", §8 #4). The same query embedded alone, then in a batch with
  long texts (different padding and matrix shapes), changed components by up to **4.3e-4**, in 71 of 100
  queries. A fresh full ingest today into a scratch database (`northwind_drift`, since dropped) left
  **3 of 2,351 stored vectors** different from the shared index's Nov 4 ingest, by up to 2.5e-4 (P0172,
  P0175, P0176). A second fresh ingest gave the same 3 differences, so today's ingests very likely agree
  with each other.
  The library versions are the same: `git log -- uv.lock` shows onnxruntime 1.31.1, fastembed 0.9.1 and
  tokenizers 0.23.3 as first locked, and no later change to them. The fresh index still gave the same macOS hash `99135472…`, so neither these 3 vectors nor
  ingest history caused this drift.
- **Ruled out:**
  - *Collation:* `ORDER BY chunk_id` under `en_US.utf8` orders all 2,351 IDs exactly as `COLLATE "C"`
    and as Python's sort.
  - *Ingest history:* the fresh ingest gave the same hash.
  - *The keyword arm:* the hash matched with dense swaps alone.
  - *Fusion:* it is exact.
  - *Image:* both use the tag `pgvector/pgvector:pg16` (local: PostgreSQL 16.15, pgvector 0.8.7, aarch64).
    **Unverified beyond the tag:** CI pulled digest `sha256:0dd3149a06e4579a0d70d8fef9945636cd514005e7237deb27f9b67886f8dc4f`.
    The local digest and CI's pgvector version were not compared (open item, owner the user).

### Recommendation: (b) + (c) + (e), plus a diagnostic line on stale

1. **(b) Frozen vectors.**
   - **The file:** `data/embeddings/bge-small-en-v1.5-384.jsonl`, one line per vector:
     `{"key": sha256(embed_text) or sha256("query:" + text), "kind": "chunk"|"query", "v": [float32 shortest repr …]}`.
   - **Size:** 2,351 chunks and about 113+ queries, roughly 10 MB of text.
   - **Why text:** the cassette scanner can read it, which a binary blob would not allow. Shortest-repr
     float32 has at most 9 significant digits, so there are no 13–19-digit runs to trip the PAN check.
   - **Export:** bit-exact from the shared `northwind` index, which produced every saved context and recording.
   - **`CachedEmbedder(inner, cache)`** implements the existing `Embedder` interface. A hit returns the frozen
     float32 vector; a miss calls fastembed.
   - **Wired into:**
     - ingest;
     - the eval CLI's `_live`, `_arms`, compare-retrievers and the enrichment report;
     - the smoke tests' retriever.
   - **The live shopper path stays unchanged**, embedding each query live, since production is never compared
     with a recording.
   - **`make embed-cache`**, with no LLM, adds entries for missing keys only and never recomputes one (as in
     `data/enrichment`).
   - **A coverage test** fails if any fixture chunk, eval query or smoke question lacks an entry.
2. **(c) Exact re-rank.**
   - `_dense` and the hybrid dense CTE fetch the top `2 × depth` (100) by `<=>` under the same `_FILTER`,
     with `embedding::text`.
   - Python parses each value to an exact float32, computes `dot = fsum(a·b)`, `na = fsum(a·a)` and
     `nb = fsum(b·b)` in float64, then `1 - dot / sqrt(na·nb)`. Each float32×float32 product is exact in
     float64, `fsum` is correctly rounded, and sqrt and division are IEEE-correct, so the result is
     bit-identical on every CPU.
   - Then sort by (distance, chunk_id) and keep the top `depth`.
   - **A margin guard:** if the exact distance at rank `depth` is not at least 1e-5 below pgvector's at rank
     100, refuse (raise) rather than guess. That never happened here.
3. **(e)** `ORDER BY …, chunk_id COLLATE "C"` in `_SEARCH`, `_KEYWORD` and both CTEs, matching
   `rrf_fuse`'s code-point tie-break.
4. **The gate prints, for each stale item**, `STALE <id> saved <5 chunk ids> live <5 chunk ids>`, IDs only
   and no text. The next drift can then be read from the CI log without a hash search. This is `evals/src`,
   under the `gate-change` label the row already carries.

- **`RETRIEVER_VERSION`:** proposed unchanged at 2, because every measured context is the same
  (decision needed: D2). Bumping it would make all 100 saved contexts stale by ID, and the baseline records
  `retriever_id`. That means `make eval-snapshot` (no LLM) and your re-promote. Answers should still replay,
  because `retriever_id` is not part of any model input (`answerers.py` does not read it), but that is
  unverified.
- **Cost:**
  - 0 cassettes re-recorded, $0 spent, no spending window;
  - about 1 day, chain included: implement 0.5, tests 0.25, then `test-writer`, a scoped `security-reviewer`
    (the `services/rag` hard-rule-7 paths), `make ci`, `make review-diff`, `advisor-reviewer` and the gate report.
- **It is not routine:**
  - it touches `services/rag/**`;
  - control-surface files: `evals/src/**`, the Makefile, probably a `conftest.py` for the smoke retriever,
    and a new `data/embeddings/` that should join the control surface as `data/enrichment` did, which is a

## 4. Making it testable

Each test is tagged `@pytest.mark.req("RAG-03")`, and each must be seen failing first, logged in
`failfirst-drift.log`.

1. **A deliberate near-tie flip, through the eval path** (integration, real index).
   - **The flip:** EV-029's query vector `q` becomes `q' = q + ε·(v_P0014 − v_P0006)`, with ε chosen so the
     P0006/P0014 dense order reverses. The test also asserts that it reversed.
   - **Without the frozen query vector:** retrieval for `q'` must change the fused top 5, a sanity check that
     the test can fail.
   - **With `CachedEmbedder` and an inner embedder that returns `q'`:** the gate's `_live` must return exactly
     the saved top 5 and the macOS fingerprint.
   - **Fails today:** `_live` has no cache.
2. **The exact re-rank ignores pgvector's order** (unit and integration). The re-rank gets the candidate
   rows in reversed and in shuffled order and must return the same IDs.
   - **Distances:** must equal an exact `Fraction` reference, rounded to float64, bit for bit.
   - **A built pair:** two float32 vectors whose float32 sequential sum orders them one way, while the exact
     distance orders them the other. The re-rank must follow the exact one.
   - **Fails today:** the order is pgvector's.
3. **Hard rule 7 is unchanged.** The re-rank never returns a chunk that is not in the filtered SQL result.
   It reuses the shopper/region tests in `test_hybrid_filters.py` across all four regions, plus a mutant
   that drops the filter from the candidate query.
4. **Cache coverage and integrity.**
   - Every fixture chunk, eval query and smoke question has an entry.
   - Every vector has 384 finite float32 values with a norm within 1e-3 of 1.
   - Ingest with the cache writes exactly the cached values.
   - A missing entry fails with the `make embed-cache` hint.
5. **Collation:** the SQL text has `COLLATE "C"`, and a Postgres check shows the clause matters. Checked
   today on the local server: `('ab:0', 'a-b:0', 'A:0', 'a:1')` sorts as `A:0, a:1, a-b:0, ab:0` under
   `en_US.utf8`, and as `A:0, a-b:0, a:1, ab:0` under `C`, which is Python's order.
6. **The stale diagnostic:** the gate output for a stale item shows saved and live IDs, and no chunk text.

**How to prove the CI hash then equals macOS:**
1. Locally, `make ci` must print `99135472f1545431c10e4b3bdab76bca3cf9eff9d233eb356d8f0486a8368074`, 100/100
   replayed and stale 0. It should stay the same, because the vectors are exported bit-exact and the
   re-rank changes no order.
2. Run the same on a fresh scratch ingest, which proves ingest takes the frozen vectors: today's fresh ingest
   left 3 vectors different.
3. Optional, from your terminal: reproduce x86 locally with `docker run --platform linux/amd64` under
   Rosetta. Before the fix it may print `0fbf3491…`. Rosetta may report AVX2 rather than the runners' AVX-512 (unverified),
   so an exact reproduction is not guaranteed, and that is why this step is optional.
4. You push. CI's `eval-gate` must print the macOS hash, 100/100 and stale 0, on both the PR and push runs.
   A different hash is stop 7 again, and this time the stale lines name the items.
5. The `e2e` job must pass on Linux with the smoke retriever on frozen vectors.

### 9.1 Changes

1. **The frozen vectors**, in `services/rag/src/northwind_rag/embedding.py`.
   - **File:** `data/embeddings/fastembed-BAAI-bge-small-en-v1.5-384.jsonl`. The name comes from the embedder id,
     with `:` and `/` turned into `-`.
   - **Lines:** `{"key": "<digest>", "vector": [384 numbers]}`, sorted by key, each key once.
   - **Keys are digit-free (H1):** the sha256 hex of the text, with `0123456789` mapped to `ghijklmnop`, as
     `data/enrichment` does (`enrichment.py:101-103,153`). The function is shared, not copied: it moves to
     `northwind_rag.embedding.digit_free_digest(text)`, and `enrichment.py` imports it, so its keys are unchanged
     (N4). A hex digest can
     hold a 13–19-digit run that passes Luhn, and the scanner allows no exemption. Load refuses a key outside
     `[a-p]{64}`.
   - **Collisions (L2):** chunks and queries share one key space, because the key is the text. A test asserts
     that no query key equals a chunk key, so a query never takes a batch-made chunk vector.
   - **Numbers (L3, L9):** each component is written as the shortest `%.{p}g` form, p ≤ 9, that reads back to the
     same float32 by `struct` round-tripping `float(text)`. That is the exact read path, so a value that does
     not read back bit-exact cannot be written: `embed-cache` refuses. No numpy, so no `pyproject.toml` or
     `uv.lock` change.
   - **Digit runs:** `%g` goes to an exponent below 1e-4. The longest digit run is then 12 (`0.000` plus 9
     digits), and `.`, `,` and `e` end a run (`_PAN_RUN`, `scan.py:52`), so no 13–19-digit run is possible.
   - **`CachedEmbedder(inner)`:**
     - `id` and `dim` are the inner embedder's (§8 #2), so `retriever_id`, the saved contexts and the baseline's
       `retriever_id` do not change, and ingest re-embeds nothing.

       through and never reads the file.
     - `embed(texts)` returns frozen vectors for hits. All misses go to `inner.embed` in one call, in order.
     - Load fails closed on bad JSON, a bad or duplicate key, a length other than `dim`, a non-finite value, or a
       norm more than 1e-3 from 1.
2. **The exact re-rank**, in `services/rag/src/northwind_rag/retrieval.py`.
   - **SQL (L7):** the dense list (`_SEARCH`, and the dense CTE in `_HYBRID`) also selects `<=>` as `pg_distance`
     and `embedding::real[]::float8[]`. That cast is exact: Postgres prints float8 in shortest round-trip form,
     measured exact on every value fetched.

     which is 100 for agents. The keyword CTE keeps `%(depth)s`. `dense_search` uses
     `pool = 2 × max(CANDIDATE_DEPTH, k)` and keeps `k`.

     `1 - fsum(a·b) / sqrt(fsum(a·a) · fsum(b·b))`.

     divides by zero.

     (or `k`).
