## 11: RAG-04 query understanding (rules first, Haiku only when needed, live filters)

## Why

- **RAG-04 asks for:** query understanding that rewrites queries, splits multi-part questions, and extracts
  structured filters (price, size, colour, availability). The criterion is filter extraction at least 95% correct on
  100 labelled queries.
- **The constraint:** decision 0007 removed a model call to cut first-token time. NFR-13 is already about 2.0 s, so
  an extra Haiku call cannot sit on every turn's first-token path.

## What this does (decision 0022)

- **Rules first, in code** (`northwind_rag.query.rules_plan`).
  - Every message gets colour, size, price and availability filters, in well under a millisecond.
  - The search text is the raw message, so a message with no filter keeps exactly its old first search.
- **Haiku only for messages the rules mark uncertain** (`northwind_assistant.understand`): several asks, a size
  question, a price with no bound, or a short follow-up.
  - Never for a message the first search would refuse (card data, hard rule 1), and never for one carrying injected
    text.
  - Haiku replies in a fixed JSON schema, and `validate_plan` checks every field in code: allow-listed, typed, the
    catalog's own vocabulary, prices as minor units in the region's own currency, part texts not card-shaped.
- **Price and availability use live data only** (hard rule 2).
  - mcp-catalog's new `eligible_products` returns product IDs only, from the live store.
  - Only the new non-model agent `shopper-query` may call it.
- **The plan reaches mcp-rag as a signed `qf` claim** on a token for that one search, with the turn's own id.
  - It is never a tool argument; the model's tools and schemas are unchanged.
  - Filters only narrow.
- **A named product runs the plain first search** (decision 0022, exception, after W5).
  - Narrowing a named product's variant question ("Is the Corvane Ridge Fleece Jacket in Glacier Blue available in
    4XL?") dropped the variant chunks that answer it.
  - Detection is by code against catalog names. Filters are still extracted.
- **The deadline and cache are live mode only:** 700 ms and an in-process LRU. Record and replay wait for every
  call and read every cassette.
- **The gate scores the planned first search** (`evals/src/northwind_evals/query_plans.py`, `cli._live`).
  - Haiku's plans replay from the new `query-understanding` suite.
  - RAG-03's arm comparison and E1 keep the plain search (`_live_plain`).
  - `RETRIEVER_VERSION` is 3.

### Deadline gap (known and accepted)

> Query understanding sends a message to Haiku only when the rules mark it uncertain. In live mode Haiku is waited for at most 700 ms (decision 0022, kept unchanged by the user); in record and replay every call is waited for. W1 measured Haiku plan time at p50 2,339 ms and p95 3,510 ms, so in live mode nearly every Haiku-routed message falls back to its rules plan. On the 100 labelled queries that is the difference between 93/100 (rules only, as live mode will mostly run) and 99/100 (rules plus Haiku, as recorded and replayed). This baseline therefore scores Haiku's plans for 7 eval items (EV-018, EV-067, EV-102, EV-190, EV-272, EV-284, EV-307) that live mode may answer with the rules plan instead. Four of those name a product and run the plain first search either way, so the difference can affect at most EV-018, EV-067 and EV-190. The gap is known and accepted, not measured in live mode.

## Known limits (not fixed here)

- **Live mode:** effectively rules-only under the 700 ms deadline (above).
- **Named-product detection** matches brand plus model word:
  - Some model words are ordinary words, so detection errs toward the plain search.
  - A product named without its brand still narrows.
- **Haiku latency:** a routed message that names a product still waits for Haiku in live mode, up to 700 ms, for a
  plan that narrows nothing.
- **RAG-04 outcome test:** "EV-042 keeps its variant chunks" is shown by the re-snapshot, not by a unit test, because
  it needs the index.
- **A2A-05 partner:** its recorder passes no query understanding. Whether it should is part of the partner-surface
